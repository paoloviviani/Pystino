# 0016 — PWA via Serwist

- Status: accepted (decision recorded; **not implemented** — Phase 2)
- Date: 2026-08-14

## Context

PWA support is mandatory, not optional. The question was Serwist versus alternatives.

## Findings (verified 2026-08-14)

- **`next-pwa` is genuinely archived.** The `ImBIOS/next-pwa` repository was archived on
  18 August 2023, and the GitLab `serwist/next-pwa` is explicitly marked Archived. Any
  tutorial recommending it is out of date.
- **Serwist** is the maintained successor by the same author who maintained the
  `@ducanh2912/next-pwa` fork. **MIT.** Built on Google's Workbox, and specifically
  described as working cleanly with Next.js 16.
- Workbox itself is described by Serwist's own README as having stagnated, which is why
  Serwist exists.

## Decision

**Serwist** (`@serwist/next` + `serwist`), with `app/manifest.ts` and `app/sw.ts`.

There is no real alternative: hand-writing a service worker means reimplementing
Workbox's caching strategies, and the archived option is archived.

## Consequences

- Serwist has ~1.5k stars and is effectively a single-maintainer project. That is a real
  risk, and it is **acceptable specifically because a service worker is replaceable**:
  it is a self-contained file at the edge of the system, not a dependency threaded through
  the application. If Serwist stalls, the cost is rewriting one file against Workbox
  directly.
- Offline behaviour needs a deliberate decision that is **not** made here: an app shell
  plus IndexedDB can show past conversations offline, but our server is authoritative for
  conversations ([0015](0015-frontend-stack.md)). Caching them client-side reintroduces
  exactly the sync problem that design avoids. Decide the offline scope before writing
  the service worker — the safe default is "shell and assets offline, conversations
  require the network".
- Streaming and service workers interact badly if the worker tries to cache or buffer
  `text/event-stream`. The `/v1` paths must be excluded from any caching strategy.
