# 0005 — PostgreSQL as the ledger of record, SQLAlchemy 2.0 async, Alembic

- Status: accepted
- Date: 2026-08-14

## Context

The gateway records money. Whatever else is true of the storage layer, a request's
cost must survive a restart, be auditable months later, and never be silently
wrong.

## Decision

**PostgreSQL** is the ledger of record. `usage_records` is the authoritative account
of what was spent; every other store (Valkey counters) is a cache derived from it and
disposable. See [0006](0006-counter-store.md).

**SQLAlchemy 2.0, pinned `>=2.0.36,<2.1`.** 2.1 is still **beta** as of 2026-06
(2.1.0b3, 27 June 2026) — do not ship it. The `<2.1` ceiling is deliberate, so a
routine `uv lock --upgrade` cannot pull a beta ORM into a service that handles
billing.

**Alembic 1.19** for migrations, with the async `env.py` variant.

### Type choices that are load-bearing

- **`Money = Numeric(24, 12)`, never float.** Cost is summed against monetary
  quotas; binary floating point cannot represent 0.01. `as_decimal()` routes floats
  through their exact string form, because `Decimal(0.1)` is
  `0.1000000000000000055511151231257827`.
- **`TZDateTime`** guarantees every datetime crossing the ORM boundary is
  timezone-aware UTC. Rolling-window quota arithmetic mixing naive and aware
  datetimes fails only under load, near midnight, or in another timezone. Binding a
  naive datetime raises rather than guessing.
- **Enums as plain `VARCHAR`, not native PostgreSQL enums** (`native_enum=False`).
  Native enums need `CREATE TYPE` and make every added value a migration with a lock.

  > **Corrected 2026-08-15.** This originally read "`VARCHAR` + `CHECK` … a CHECK
  > constraint gives the same protection", which was wrong. SQLAlchemy's
  > `Enum(native_enum=False)` defaults to `create_constraint=False`, so no CHECK is
  > emitted and the column is a bare `VARCHAR` — verified against the live database,
  > which has only the three constraints this schema names explicitly. Values are
  > validated in the application (`validate_strings=True`), not by the database.
  >
  > Left as it is, deliberately. Adding the CHECK would restore the protection and
  > reintroduce exactly the cost the decision was avoiding: a CHECK has to be dropped
  > and recreated to add a value, which is the same migration-with-a-lock as a native
  > enum. Adding `api_key` to `LimitScope` in migration 0002 needed no DDL at all,
  > which is the benefit in practice. The trade accepted: a bad value written by
  > something other than the application is not rejected by the database.
- **Identity foreign keys are nullable with `ON DELETE SET NULL`.** Erasing a user
  under GDPR Art. 17 must not require deleting or falsifying the financial ledger.
  `model_name` is denormalised onto every usage row for the same reason.

### Alembic specifics

Two wrinkles, both handled:

1. Alembic's generated `env.py` calls `engine_from_config()`, which builds a
   *synchronous* engine and cannot use `asyncpg`. `env.py` creates an async engine
   and runs the migration through `connection.run_sync`.
2. Autogenerate rendered our `TZDateTime` TypeDecorator as
   `gateway.types.TZDateTime(...)`, which fails with `NameError` — and worse, would
   make every historical migration depend on application code that is free to
   change. A `render_item` hook renders it as `sa.DateTime(timezone=True)`. **A
   migration describes SQL; it must not import the app.**

`render_as_batch=True` is set so migrations also apply on SQLite, which the test
suite uses.

## Verified on real PostgreSQL 18 (2026-08-14)

The migration was applied by the compose stack against `postgres:18-alpine`, and the
resulting schema inspected:

- 9 tables plus `alembic_version`; Alembic reported `Context impl PostgresqlImpl` and
  transactional DDL.
- `usage_records.cost` is `numeric(24,12)` — not a float.
- `usage_records.created_at` is `timestamp with time zone`.
- The portable enum approach produced real `CHECK` constraints, including
  `ck_limit_rules_scope_id_presence`.

**One deployment trap found by running it.** From PostgreSQL 18 the official image
**refuses to start** if the data volume is mounted at `/var/lib/postgresql/data`,
which was the convention for every earlier version. It now stores data in a
major-version-specific subdirectory so that `pg_upgrade --link` need not cross a
mount boundary, and expects a single mount one level up at `/var/lib/postgresql`. The
error is easy to misread as data corruption:

```
Error: ... there appears to be PostgreSQL data in:
  /var/lib/postgresql/data (unused mount/volume)
```

`deploy/compose/docker-compose.yml` mounts `/var/lib/postgresql` and carries a
comment explaining why, because the instinct on seeing it is to "fix" it back.

## Consequences

- The initial migration (`0001_initial_schema`) was autogenerated from the ORM and
  verified to apply and roll back cleanly: 9 tables created and dropped (on SQLite),
  and applied cleanly on PostgreSQL 18 (above).
- **Tests run on SQLite**, which cannot store `Numeric` natively. Exact monetary
  arithmetic is therefore tested as pure `Decimal` functions in `test_cost.py`, and
  database-level tests use values that survive a float round-trip. Verifying the
  schema on real PostgreSQL is the migration's job and `docker compose`'s.
- **The database URL is not in `alembic.ini`.** `env.py` reads it from
  `gateway.config`, so migrations and the running service cannot be pointed at
  different databases. `-x url=...` overrides it for one-off work.
- Money precision is 12 decimal places. Per-token prices run to ~1e-9 and a single
  request to ~1e0, so there is headroom without rounding mid-calculation.
